# Chunk Search Strategy

## Hybrid Search: Keyword + Semantic

Two search modes over extracted chunks, matched to field characteristics.

### Keyword Search: `topic` + `tags`

- `tags` are normalized tokens (`learning-tests`, `backpressure`, `CI-CD`) — good for exact/fuzzy keyword matching
- `topic` is a short, dense label — keyword hits here are high-signal
- Both fields are low-noise, so keyword precision stays high

### Semantic Search: `summary` + `key_insights`

- Natural language with nuance that keyword search misses (e.g., "how to give AI agents feedback" should match backpressure chunks)
- Key insights contain quotes and analogies that carry meaning beyond literal words (e.g., "print debugging is just a learning test")

### Metadata Filters (not search targets)

- `chunk_id`, `episode` — scope queries ("chunks from this episode") but don't rank relevance
- `speakers` — useful as a filter ("what did Vaibhav say about type systems")

### Ranking Considerations

- Keyword hit on `tags` should rank higher than on `topic` (tags are curated)
- Semantic match on `summary` is more holistic than a single `key_insight` bullet
- Cross-field boosting: keyword match in tags AND high semantic score on summary = very strong signal
- Simple fusion: `keyword_score + semantic_score`

## Implementation Notes: Postgres (Neon)

### Keyword Search — Postgres Full-Text Search (tsvector/tsquery)

Postgres has built-in full-text search using `tsvector` and `tsquery`. This is **not BM25** — it uses a simpler tf-based ranking (`ts_rank`) — but it handles the job well for this scale.

**Hyphenated tags and full-text search:**

Postgres' `to_tsvector()` parser treats hyphens as word separators by default. So:

- `'learning-tests'` gets tokenized into two lexemes: `'learn'` and `'test'` (after stemming)
- `'CI-CD'` becomes `'ci'` and `'cd'`
- `'LLM-as-judge'` becomes `'llm'`, `'judg'`

[comment] This means a search for `learning` will match `learning-tests`, which is probably desirable — you get partial matching for free. But it also means `learning-tests` as an exact phrase isn't preserved as a single token.

**Options:**

1. **Do nothing** — the default tokenization is probably fine. Searching "learning tests" matches chunks tagged `learning-tests`. Most useful behavior.
2. **Store a parallel field with hyphens replaced by spaces** — no real benefit over option 1 since the parser already splits on hyphens.
3. **Store tags as-is in an array column (`text[]`)** and use `@>` array containment for exact tag matching, **in addition to** the tsvector column for fuzzy full-text search. This gives you both exact and fuzzy paths.

[suggestion] Option 3 (array column + tsvector) is the most flexible — exact tag filtering when the user picks from a tag list, full-text search when they type free text.

### Semantic Search — pgvector on Neon

Neon supports the `pgvector` extension. Store embeddings for `summary` and `key_insights` and use cosine similarity search.

### Hybrid Query Pattern

```sql
-- Combine keyword + semantic scores
WITH keyword AS (
  SELECT chunk_id,
         ts_rank(search_vector, plainto_tsquery('english', $1)) AS kw_score
  FROM chunks
  WHERE search_vector @@ plainto_tsquery('english', $1)
),
semantic AS (
  SELECT chunk_id,
         1 - (embedding <=> $2::vector) AS sem_score
  FROM chunks
  ORDER BY embedding <=> $2::vector
  LIMIT 20
)
SELECT COALESCE(k.chunk_id, s.chunk_id) AS chunk_id,
       COALESCE(k.kw_score, 0) * 0.4 + COALESCE(s.sem_score, 0) * 0.6 AS score
FROM keyword k
FULL OUTER JOIN semantic s USING (chunk_id)
ORDER BY score DESC
LIMIT 10;
```

[suggestion] Weights (0.4 / 0.6) are a starting point — tune based on query patterns once real usage data exists.

## Clarification: tsvector vs. pgvector

Confusing names, but completely different technologies.

### tsvector (Keyword Search)

**Not a vector embedding.** `tsvector` is Postgres' internal data type for full-text search — a sorted list of normalized lexemes (stemmed words + their positions). No neural network, no embeddings — just text processing.

```sql
SELECT to_tsvector('english', 'learning-tests in practice');
-- Result: 'learn':1 'practic':3 'test':2
```

It strips stop words ("in"), stems words ("learning" → "learn", "practice" → "practic"), and records positions.

`tsquery` is the matching query type:

```sql
SELECT to_tsvector('english', 'learning-tests in practice')
    @@ plainto_tsquery('english', 'learning tests');
-- Result: true
```

### pgvector (Semantic Search)

Actual vector embeddings generated by an external embedding model (e.g., OpenAI, Cohere). Stored as a `vector` column type. Searched via cosine similarity (`<=>` operator).

### Summary

| Layer | Tech | What it actually is |
|-------|------|-------------------|
| Keyword search | `tsvector` / `tsquery` | Stemmed word lists + position matching. Classic text search. |
| Semantic search | `pgvector` | Actual vector embeddings (from an embedding model). Cosine similarity. |

Two totally separate Postgres features that happen to both use the word "vector."
